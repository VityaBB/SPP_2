# Лабораторная работа №3 — роли, временные ключи и защита доступа

Приложение развивает SPA + REST API из лабораторной работы №2. Клиентский
интерфейс и его оформление сохранены; добавлены серверная ролевая модель,
временные ключи доступа, защита от подбора учётных данных, контроль активных
подключений, восстановление доступа по email и структурированное логирование.

## Что реализовано по требованиям ЛР3

| Требование | Реализация |
|------------|------------|
| Модель доступа минимум с 3 ролями на основе временных ключей | Роли `admin`, `manager`, `user`; access-ключ на 15 минут, refresh-ключ на 7 дней, серверные сессии |
| Ошибки и коды возврата по семантике HTTP | `200/201/202/204` для успеха, `400/401/403/404/405/409/413/415/422/429/500` для ошибок, `problem+json` (RFC 9457), заголовки `Allow`, `WWW-Authenticate`, `Retry-After`, `Location` |
| Защита от подбора, контроль подключений, восстановление по email | Блокировка после 5 неверных паролей, лимиты по IP, управление сессиями через API и отзыв сеансов администратором, одноразовые ссылки восстановления через MailHog |
| Структурированное логирование | JSON-строка на событие, `requestId`, метод/путь/статус/длительность, журнал безопасности в SQLite |
| Автоматизированная проверка кода | ESLint 9, `node --test` + supertest, единая команда `npm run check`, GitHub Actions |

## Архитектура

```
Браузер (SPA, hash-роутинг)
        │  http://localhost:3000
        ▼
┌──────────────────┐   /api/*   ┌──────────────────────────┐
│  web: nginx      │ ─────────▶ │  api: Node.js/Express    │
│  HTML/CSS/JS     │            │  REST, RBAC, сессии      │
└──────────────────┘            └────────────┬─────────────┘
                                             │
                       ┌─────────────────────┼─────────────────────┐
                       ▼                     ▼                     ▼
               SQLite (lab3-data)    файлы (lab3-uploads)   MailHog (SMTP)
```

* Клиент — SPA без сборки и внешних CDN: hash-роутинг, `fetch`, обновление
  данных без перезагрузки страницы.
* Сервер — Node.js + Express, SQLite (`better-sqlite3`), Multer для
  `multipart/form-data`.
* Docker — отдельный проект `lab3` с контейнерами `lab3-api`, `lab3-web`,
  `lab3-mailhog` и томами `lab3-data`, `lab3-uploads`. Стек ЛР2 не изменяется.

## Демонстрационные учётные записи

Создаются при первом запуске (`SEED_DEMO_USERS=true`):

| Роль | Email | Пароль |
|------|-------|--------|
| Администратор | `admin@example.com` | `Admin123!` |
| Менеджер | `manager@example.com` | `Manager123!` |
| Пользователь | `user@example.com` | `User123!` |
| Пользователь | `user2@example.com` | `User123!` |

## Самостоятельная регистрация

На экране входа есть ссылка **«Создать учётную запись»** (`#/register`).
Новый пользователь указывает имя, email и пароль; после создания учётной
записи он сразу входит в систему.

* Самостоятельная регистрация всегда создаёт роль **`user`**. Поле `role` в
  запросе запрещено: попытка передать его возвращает `422`, чтобы нельзя было
  выдать себе права администратора.
* Email должен быть уникальным: повторная регистрация возвращает `409
  Conflict`.
* Пароль — от 8 до 128 символов, содержит хотя бы одну букву и одну цифру.
* Регистрация ограничена по IP: **5 попыток в час** по умолчанию, при
  превышении — `429` с `Retry-After`.
* События `auth.register` и `auth.register.failed` попадают в журнал аудита.
* Повысить роль нового пользователя может только администратор в разделе
  **«Пользователи»** или через `PATCH /api/users/:id`.

## Роли и права

| Действие | `user` | `manager` | `admin` |
|----------|:------:|:---------:|:-------:|
| Видеть свои задачи | да | да | да |
| Видеть задачи всех пользователей | нет | да | да |
| Создавать задачи | да | да | да |
| Назначать владельца задачи | нет | нет | да |
| Управлять пользователями | нет | нет | да |
| Видеть и отзывать любые сессии | нет | нет | да |
| Читать журнал аудита | нет | нет | да |

Пользователь видит и изменяет только собственные задачи. Менеджер и
администратор видят все задачи; менеджер не может менять владельца, а
администратор может. Администратор не может заблокировать или удалить сам
себя, а также лишить систему последнего активного администратора.

## Временные ключи и сессии

* **Access-ключ** — случайные 32 байта, передаётся в
  `Authorization: Bearer <token>`, живёт 15 минут. В БД хранится только SHA-256
  хеш ключа.
* **Refresh-ключ** — случайные 48 байт, хранится в cookie
  `lab3_refresh` с `HttpOnly`, `SameSite=Strict`, `Path=/api/auth`; живёт
  7 дней. В БД хранится хеш.
* При `/api/auth/refresh` refresh-ключ **ротируется**: выдаётся новая пара
  ключей, старый refresh помечается использованным. Повторное использование
  старого ключа трактуется как компрометация и отзывает все сессии
  пользователя.
* Клиент хранит access-ключ только в памяти и при старте восстанавливает
  сессию через refresh-cookie. При `401` выполняется одна попытка обновления
  ключа и повтор запроса.
* Отдельный раздел «Подключения» в клиенте не отображается. Активные сессии
  доступны через API `/api/auth/sessions` и `/api/sessions`; администратор
  может завершить все сеансы пользователя кнопкой в разделе «Пользователи».
* Смена или восстановление пароля, блокировка и удаление пользователя
  отзывают его сессии.

## Защита от подбора учётных данных

* После **5 неверных паролей за 15 минут** учётная запись блокируется на
  15 минут. Ответ — `429 Too Many Requests` с `Retry-After`.
* Отдельный лимит на вход — **10 попыток за 10 минут с одного IP**.
* Запросы восстановления — **10 в час с одного IP**.
* Общий лимит API — **300 запросов в минуту с одного IP**.
* Для несуществующего email выполняется проверка фиктивного хеша, поэтому
  время ответа не выдаёт наличие учётной записи. Ответы на неверный пароль и
  неизвестный email одинаковы.
* Восстановление пароля снимает блокировку; администратор может снять её
  вручную (`POST /api/users/:id/unlock`).
* Блокировка по паролю дополняется IP-лимитами, поэтому перебор с одного
  адреса ограничен и на уровне учётной записи, и на уровне сети.

## Восстановление доступа по email

1. Пользователь вводит email на экране «Забыли пароль?».
2. Сервер всегда отвечает `202 Accepted` с нейтральным сообщением — факт
   существования учётной записи не раскрывается.
3. Для существующего активного пользователя создаётся одноразовый ключ на
   30 минут; предыдущие ключи этого пользователя инвалидируются. В БД
   хранится только хеш.
4. Письмо со ссылкой
   `http://localhost:3000/#/reset-password?token=...` отправляется через SMTP
   (MailHog) или выводится в лог в dev-режиме.
5. После установки нового пароля ключ помечается использованным, все сессии
   пользователя отзываются, блокировка снимается.

В Docker письма видны в MailHog: **http://localhost:8025**.

## HTTP-семантика

Успешные ответы:

| Код | Когда используется |
|-----|--------------------|
| `200 OK` | чтение, обновление, вход, refresh |
| `201 Created` | создание задачи, пользователя, загрузка файла; с `Location` |
| `202 Accepted` | запрос восстановления пароля |
| `204 No Content` | удаление, выход, смена пароля, отзыв сессии |

Ошибки:

| Код | Пример |
|-----|--------|
| `400 Bad Request` | некорректный JSON, идентификатор, query-параметр |
| `401 Unauthorized` | нет/истёк access-ключ; ответ содержит `WWW-Authenticate` |
| `403 Forbidden` | недостаточно прав, недоверенный `Origin`, заблокированная учётная запись |
| `404 Not Found` | задача, файл, пользователь или сессия не найдены |
| `405 Method Not Allowed` | неподдерживаемый метод; ответ содержит `Allow` |
| `409 Conflict` | дубликат email, удаление пользователя с задачами, последний администратор |
| `413 Payload Too Large` | слишком большой файл или JSON |
| `415 Unsupported Media Type` | не JSON там, где требуется JSON; недопустимый тип файла |
| `422 Unprocessable Content` | ошибки валидации полей, слабый пароль |
| `429 Too Many Requests` | лимит частоты или блокировка после подбора; есть `Retry-After` |
| `500 Internal Server Error` | внутренняя ошибка без раскрытия деталей |

Ошибки возвращаются в формате `application/problem+json` (RFC 9457):

```json
{
  "type": "about:blank",
  "title": "Ошибка валидации",
  "status": 422,
  "detail": "Данные не прошли проверку",
  "instance": "/api/tasks",
  "requestId": "0f5f0f0e-7a4f-4a4e-9d4e-7a1a2b3c4d5e",
  "errors": [
    { "field": "title", "message": "title не может быть пустым" }
  ]
}
```

Дополнительно:

* Для state-changing запросов проверяется `Origin`; запросы с чужого origin
  отклоняются с `403`.
* API отдаёт `Cache-Control: no-store` и security-заголовки
  (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Cross-Origin-Resource-Policy`); nginx добавляет CSP.
* `X-Request-ID` возвращается клиенту и связывает ответ с записями логов.

## REST API

Базовый префикс — `/api`. Все маршруты задач, пользователей, сессий и аудита
требуют `Authorization: Bearer <accessToken>`; для `/api/auth/register`,
`/api/auth/login`, `/api/auth/refresh`, `/api/auth/forgot-password` и
`/api/auth/reset-password` ключ не нужен.

### Аутентификация и сессии

| Метод | Маршрут | Назначение | Успех |
|-------|---------|------------|-------|
| POST | `/api/auth/register` | Публичная регистрация с ролью `user` | 201 |
| POST | `/api/auth/login` | Вход, выдача access/refresh-ключей | 200 |
| POST | `/api/auth/refresh` | Ротация refresh-ключа | 200 |
| POST | `/api/auth/logout` | Завершить текущую сессию | 204 |
| GET | `/api/auth/me` | Текущий пользователь и сессия | 200 |
| GET | `/api/auth/sessions` | Свои активные подключения | 200 |
| DELETE | `/api/auth/sessions` | Завершить все другие подключения | 204 |
| DELETE | `/api/auth/sessions/:id` | Завершить своё подключение | 204 |
| POST | `/api/auth/change-password` | Смена пароля с проверкой текущего | 204 |
| POST | `/api/auth/forgot-password` | Запросить ссылку восстановления | 202 |
| POST | `/api/auth/reset-password` | Установить пароль по одноразовому ключу | 204 |

| Метод | Маршрут | Назначение | Успех |
|-------|---------|------------|-------|
| GET | `/api/tasks?status=&q=` | Список задач с учётом роли | 200 |
| POST | `/api/tasks` | Создать задачу | 201 |
| GET | `/api/tasks/:id` | Одна задача с файлами | 200 |
| PUT | `/api/tasks/:id` | Полное обновление (`title` обязателен) | 200 |
| PATCH | `/api/tasks/:id` | Частичное обновление | 200 |
| DELETE | `/api/tasks/:id` | Удалить задачу и её файлы | 204 |
| GET | `/api/tasks/:id/files` | Список файлов задачи | 200 |
| POST | `/api/tasks/:id/files` | Загрузить файл (поле `file`) | 201 |

| Метод | Маршрут | Назначение | Успех |
|-------|---------|------------|-------|
| GET | `/api/users?role=&search=` | Список пользователей | 200 |

### Пример входа и запроса

```bash
curl -i -c cookies.txt -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"User123!"}'

TOKEN="<accessToken из ответа>"

curl -i http://localhost:3000/api/tasks \
  -H "Authorization: Bearer $TOKEN"

curl -i -X POST http://localhost:3000/api/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Подготовить отчёт","status":"new","dueDate":"2026-12-01"}'

curl -i -X POST http://localhost:3000/api/tasks/1/files \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@report.pdf"
```

PowerShell:

```powershell
$login = Invoke-RestMethod -Method Post http://localhost:3000/api/auth/login `
  -ContentType "application/json" `
  -Body (@{ email = "user@example.com"; password = "User123!" } | ConvertTo-Json)

$headers = @{ Authorization = "Bearer $($login.accessToken)" }

Invoke-RestMethod http://localhost:3000/api/tasks -Headers $headers

Invoke-RestMethod -Method Post http://localhost:3000/api/tasks -Headers $headers `
  -ContentType "application/json" `
  -Body (@{ title = "Подготовить отчёт"; status = "new" } | ConvertTo-Json)
```

## Валидация

* `title` — от 1 до 200 символов после обрезки пробелов.
* `status` — только `new`, `in_progress`, `done`.
* `dueDate` — `null`, пустая строка или реальная дата `YYYY-MM-DD`
  (например, `2026-02-31` отклоняется).
* `ownerId` — положительное целое; назначать владельца может только `admin`.
* Неизвестные поля в JSON запрещены.
* Идентификаторы — только положительные целые числа.
* JSON-тело — не более 100 КБ.
* Email — корректный адрес до 254 символов, приводится к нижнему регистру.
* Пароль — от 8 до 128 символов, содержит хотя бы одну букву и одну цифру.
* Файлы — до 10 МБ; разрешены PNG/JPEG/GIF/WebP, PDF, TXT, CSV, ZIP,
  DOC/DOCX, XLS/XLSX. Проверяются MIME-тип и расширение.
* Загрузка принимает строго `multipart/form-data`; JSON-маршруты — строго
  `application/json`.

## Структурированное логирование

Каждая запись — отдельная JSON-строка в stdout:

```json
{"time":"2026-11-19T08:29:58.801Z","level":"info","msg":"request","requestId":"fda93204-6550-458a-82a2-3de85e08d814","method":"GET","path":"/api/health","status":200,"durationMs":1.2,"ip":"127.0.0.1","userId":null,"userAgent":"Mozilla/5.0 ..."}
```

Поля: `time`, `level`, `msg`, `requestId`, `method`, `path`, `status`,
`durationMs`, `ip`, `userId`, `userAgent`. События безопасности пишутся с
префиксом `audit.` (`audit.auth.login.success`, `audit.task.created`,
`audit.file.uploaded` и т. д.).

Пароли, токены, cookie, `Authorization` и хеши паролей маскируются как
`[REDACTED]`. Журнал безопасности хранится в таблице `audit_log` и доступен
администратору через `GET /api/audit`.

Пример просмотра логов контейнера:

```bash
docker compose logs -f api | Select-String '"level":"(warn|error)"'
```

### CI

Workflow находится в `lab3/.github/workflows/ci.yml`: на каждый `push` и
`pull_request` он устанавливает зависимости, запускает линтер, тесты и
собирает Docker-образы. GitHub Actions читает workflow из корня репозитория,
поэтому при сдаче папки `lab3` как отдельного репозитория файл уже находится
в нужном месте; при размещении `lab3` внутри общего репозитория workflow
нужно перенести в корневой `.github/workflows/`.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `NODE_ENV` | `development` | Режим работы |
| `PORT` | `3000` | Порт API |
| `HOST` | `0.0.0.0` | Интерфейс прослушивания |
| `APP_ORIGIN` | `http://localhost:3000` | Доверенный origin для ссылок и CSRF-проверки |
| `CORS_ORIGIN` | не задана | Разрешённые origin через запятую |
| `DATA_DIR` | `server/data` | Каталог SQLite |
| `UPLOAD_DIR` | `server/uploads` | Каталог файлов |
| `MAX_FILE_SIZE` | `10485760` | Максимальный размер файла |
| `MAX_JSON_BODY` | `100kb` | Максимальный размер JSON |
| `ACCESS_TOKEN_TTL_MS` | `900000` (15 мин) | Срок access-ключа |
| `REFRESH_TOKEN_TTL_MS` | `604800000` (7 дней) | Срок refresh-ключа |
| `RESET_TOKEN_TTL_MS` | `1800000` (30 мин) | Срок ключа восстановления |
| `LOGIN_MAX_ATTEMPTS` | `5` | Неверных паролей до блокировки |
| `LOGIN_LOCK_MS` | `900000` | Длительность блокировки |
| `LOGIN_WINDOW_MS` | `900000` | Окно подсчёта неверных паролей |
| `PASSWORD_MIN_LENGTH` | `8` | Минимальная длина пароля |
| `RATE_LIMIT_WINDOW_MS` | `60000` | Окно общего лимита |
| `RATE_LIMIT_MAX` | `300` | Общий лимит запросов |
| `LOGIN_RATE_WINDOW_MS` | `600000` | Окно лимита входа |
| `LOGIN_RATE_MAX` | `10` | Лимит попыток входа с IP |
| `MAIL_RATE_WINDOW_MS` | `3600000` | Окно лимита восстановления |
| `MAIL_RATE_MAX` | `10` | Лимит запросов восстановления с IP |
| `REGISTER_RATE_WINDOW_MS` | `3600000` | Окно лимита регистрации |
| `REGISTER_RATE_MAX` | `5` | Лимит регистраций с IP |
| `COOKIE_SECURE` | `true` в production | Флаг `Secure` для refresh-cookie |
| `TRUST_PROXY` | `1` | Число доверенных прокси |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error`, `silent` |
| `SEED_DEMO_USERS` | `true` | Создавать демонстрационные учётки |
| `SMTP_HOST` | не задан | SMTP-сервер; без него письма идут в лог |
| `SMTP_PORT` | `1025` | Порт SMTP |
| `SMTP_SECURE` | `false` | TLS для SMTP |
| `SMTP_USER` / `SMTP_PASS` | не заданы | Аутентификация SMTP |
| `MAIL_FROM` | `Список задач <no-reply@lab3.local>` | Отправитель писем |

В Docker используются тома `lab3-data` и `lab3-uploads`, поэтому перезапуск
контейнеров ЛР3 не удаляет данные и не затрагивает ЛР2.

## Отличия от ЛР2

| ЛР2 | ЛР3 |
|-----|-----|
| Нет аутентификации | Вход по email/паролю, временные access/refresh-ключи |
| Нет ролей | `admin`, `manager`, `user` с разграничением задач и администрирования |
| Задачи доступны всем | Пользователь видит только свои, менеджер и администратор — все |
| Нет контроля подключений | Управление сессиями через API, отзыв сеансов пользователя администратором |
| Нет защиты от подбора | Блокировка учётной записи, лимиты по IP, `429` + `Retry-After` |
| Нет восстановления доступа | Одноразовые ссылки на 30 минут через email/MailHog |
| Ошибки в произвольном формате | `application/problem+json` и корректные HTTP-коды |
| Логи не структурированы | JSON-логи с `requestId` и журнал аудита |
| Нет автоматических проверок | ESLint, 32 теста, GitHub Actions |
| Стек `lab2` | Отдельный стек `lab3` с MailHog |
